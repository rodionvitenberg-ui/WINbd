# Фаза 9 — Полировка, UI-пробелы и подготовка к сдаче

> Учебник фазы: почему «редактирование — это тот же редактор», зачем нужен
> отдельный компонент карточки, и как проверить проект перед сдачей.

---

## 1. Какая была ситуация

К концу фазы 8 проект выглядел так:

- Backend **полностью** закрывал ТЗ: CRUD новостей, отложенная публикация,
  загрузка файлов, real-time, JWT-авторизация.
- Frontend умел **создавать** статью (блочный редактор, предпросмотр,
  публикация сейчас/по дате), показывать её и получать уведомления в колокольчик.

Но из UI нельзя было:

1. **Отредактировать** уже созданную новость (редактор всегда создавал новую);
2. **Удалить** новость (на странице новости не было кнопки);
3. Посмотреть **свои новости** (черновики, отложенные, опубликованные вместе).

Это ровно те «3 UI-пробела», о которых писал предыдущий разработчик в HANDOVER.md.

## 2. Почему backend не пришлось трогать

Ключевая идея архитектуры «request → route → controller → model → БД → response»:
**бизнес-логика живёт в бэкенде, а фронтенд лишь вызывает уже готовые endpoints.**

Смотрим на контроллер `news.controller.js`:

- `GET /api/news/:id` — автор видит ЛЮБУЮ свою новость (даже черновик).
- `PUT /api/news/:id` — обновление, только автор.
- `DELETE /api/news/:id` — удаление, только автор.
- `GET /api/news?all=1` — все свои новости (черновики + отложенные + опубликованные).

Ни один из этих endpoints не пришлось писать или менять. Мы только «подключили»
их в интерфейс. Это и есть главный вывод фазы: **хороший backend заранее
проектируется под потенциальные UI-сценарии** (`?all=1` спроектировали ещё в фазе 3).

## 3. Редактирование новости: «тот же редактор, другой режим»

### Проблема

`Editor.tsx` всегда вызывал `POST /api/news`, то есть создавал новую статью.
Чтобы редактировать, редактор должен:

1. Знать id существующей новости;
2. Загрузить её и подставить `title`, `blocks`, дату в поля;
3. При сохранении вызвать `PUT /api/news/:id`.

### Решение

**Один редактор, два режима.** Не стали делать отдельную страницу
`/news/[id]/edit` — это дублирование кода и лишний маршрут. Вместо этого:

1. `editor/page.tsx` читает query-параметр `id` из URL (`/editor?id=...`).
   В браузере это делается через `window.location.search` + `URLSearchParams`
   (без `useSearchParams`, чтобы не оборачивать страницу в `<Suspense>` —
   у нас и так всё грузится на клиенте после авторизации).
   Если `id` есть — грузим новость `GET /api/news/:id` и передаём её в `<Editor initialNews={...} />`.

2. `Editor.tsx` принимает проп `initialNews?: News`:
   - `useState(initialNews?.title ?? '')` — заголовок из новости;
   - `useState(initialNews?.blocks ?? [])` — блоки из новости;
   - в `save()`: `initialNews ? PUT /api/news/:id : POST /api/news`.

3. Хелпер `toDatetimeLocal()` переводит ISO-дату бэкенда (`2026-08-13T12:00:00.000Z`)
   в формат `input[type=datetime-local]` → `2026-08-13T18:00` по **локальному** времени.
   Почему локально: `datetime-local` не понимает пояс (букву `Z` и смещение),
   а пользователь должен видеть время в своей таймзоне.

### Почему так, а не иначе

- **Альтернатива:** отдельная страница «редактирования» — потребовала бы
  копировать весь редактор или выносить общий хук. Один `Editor` с пропом
  `initialNews` проще и не дублирует логику.
- **Альтернатива:** сохранять через «save API» типа `saveDraft`/`publish`
  на клиенте — лишняя прослойка. Backend уже умеет различать: `publishNow: true`
  публикует, `publishAt` откладывает.

## 4. Удаление из UI: кнопка только у автора

### Почему проверяем «право автора» на клиенте, если оно есть на бэкенде?

Бэкенд ВСЕГДА проверяет: `news.author.toString() !== req.user.userId` → 403.
Клиентская проверка — это **UX**, а не безопасность: не показываем кнопку «Удалить»
человеку, которому бэкенд всё равно откажет.

```tsx
const isAuthor = Boolean(user && news && user._id === news.author);
```

`user._id` берём из `AuthContext` (пользователь восстанавливается через
`GET /api/auth/me` ← токен JWT). `news.author` — строка id автора, которую
возвращает бэкенд. Совпали — показываем кнопки.

### Поток удаления

1. `window.confirm('Удалить новость навсегда?')` — стандартный диалог браузера,
   без лишнего UI (для учебного проекта это нормально и просто).
2. `apiClient.delete('/api/news/' + id)` — авторизация добавится автоматически
   axios-интерцептором.
3. Успех → `router.push('/')` — возврат на главную.
4. Ошибка → показываем `error-text`.

### Почему `useRouter` для перехода

`router.push` из `next/navigation` — программная навигация без перезагрузки
страницы (это SPA, а не классический `<a href>`).

## 5. «Мои новости»: вкладки и переиспользуемая карточка

### Поток на главной

- Пользователь не авторизован — видит только «Все» (публичный список,
  `GET /api/news`).
- Авторизован — появляются вкладки **«Все» / «Мои»**.
  «Мои» грузят `GET /api/news?all=1` — backend отдаёт черновики, отложенные
  и опубликованные статьи автора.

Почему `all=1` требовал токен: `router.use(authMiddleware)` в `news.routes.js`
защищает ВСЕ endpoints новостей. Без токена `all=1` не имело бы смысла —
«все свои» определяется по `author: req.user.userId` из JWT.

### Компонент `NewsCard`

Вынесли карточку из `page.tsx` в `frontend/src/components/news/NewsCard.tsx`,
потому что:

- она используется в двух режимах (публичная / «Мои»);
- у неё появилась логика: бейдж статуса, кнопки, удаление, публикация;
- `page.tsx` остаётся тонким: загрузка списка + фильтр вкладок.

### Бейдж статуса по правилам ADR 0001

`News` в режиме «Мои» может иметь `status: 'draft' | 'published'` и `publishAt`.
«Отложено» — это не отдельный статус в базе! Это черновик, у которого
`publishAt` в будущем. Поэтому бейдж вычисляется:

```tsx
if (item.status === 'published') → «Опубликовано»
else if (new Date(item.publishAt) > Date.now()) → «Отложено»
else → «Черновик»
```

Именно эту логику заложил ADR 0001: **публикация — это данные, а не таймер**.

### Кнопки в «Моих»

- **Редактировать** → `/editor?id=...` (шаг 3);
- **Опубликовать** → `PUT /api/news/:id` c `{ publishNow: true }` — бэкенд
  сразу ставит `status: 'published'`, `publishAt = now`;
- **Удалить** → confirm + `DELETE`.

После удаления/публикации карточка исчезает из списка через колбэк `onDeleted`
(родитель фильтрует массив `news`). Публикацию можно было бы и «перерисовать»
бейджем, но проще перезагрузить список — сценарий редкий.

## 6. Полировка: скилл impeccable-design-polish

По правилам `.clinerules.md` после завершения UI обязательно прогоняем скилл
`impeccable-design-polish`. Он заставляет проверить: иерархию, отступы, цвет,
типографику, состояния, адаптивность, доступность.

Что было найдено и исправлено в `frontend/src/styles/_components.scss`:

1. **`btn--ghost:hover` краснел всегда.** Раньше это было «нейтральное» действие,
   но теперь в «Моих» появились кнопки «Редактировать» и «Опубликовать» —
   красный при наведении создавал ложное ощущение опасности. Решение: нейтральный
   hover у `btn--ghost` — акцент (`$accent`), а красный вынесен в отдельный
   класс `btn--danger` (только для удаления).

2. **Фокус-кольца для клавиатуры.** У кликабельной части карточки
   (`.news-card__link`) и у кнопки колокольчика (`.bell__btn`) появился
   `:focus-visible` — без него Tab-навигация «слепая».

3. **Fade-up появление карточек.** DESIGN.md обещает лёгкий fade-up
   (`opacity 0→1`, `translateY(8px→0)`). Добавлена анимация `news-card-in`
   и отключение в `prefers-reduced-motion`.

4. **Мобильная адаптивность.** Панель колокольчика может вылезать за экран —
   `max-width: calc(100vw - 24px)`. Шапка, футер карточки и кнопки редактора
   складываются в колонку на `max-width: 640px`.

5. **Бейджи статусов** по DESIGN.md: зелёный/синий/жёлтый с полупрозрачной
   заливкой.

## 7. Полное тестирование по скиллу diagnosing-bugs

Перед сдачей был прогон по скиллу `skills2/diagnosing-bugs/SKILL.md` —
«построй плотный feedback loop, заставь его покраснеть, почини».

### Что дало красный сигнал

Временный e2e-скрипт `backend/test-e2e.tmp.js` (39 проверок: health, CORS,
auth, news CRUD, отложенная публикация, права автора, валидации, пагинация,
upload, socket) прогонялся против живого сервера. Первый прогон показал:

- `✗ черновик НЕ в публичном списке — Cannot read properties of undefined`
- `✗ published виден в публичном списке — ...`
- `✗ отложенная НЕ в публичном списке — ...`
- `✗ GET с невалидным id → НЕ 500 ...`
- `✗ limit ограничен 50, пустая страница → news=[]`

Это свелось к **двум реальным багам**.

### Баг A: публичный список новостей требовал токен

**Симптом:** `GET /api/news` без токена → 401. Главная страница для
неавторизованного пользователя не работала.

**Причина:** в `news.routes.js` стоял `router.use(authMiddleware)` — строгий
middleware вешался на ВСЕ маршруты, включая публичное чтение. Но контроллер
`getNews` изначально проектировался так: публичный список (без `all`) доступен
всем, а `?all=1` («свои») — только автору.

**Решение:** создан `optionalAuth.middleware.js` — «мягкая» проверка токена:
если JWT валиден — кладёт `req.user`, если нет — просто вызывает `next()`
(гость). В роутере POST/PUT/DELETE остались на `authMiddleware`, а GET переведён
на `optionalAuthMiddleware`. Контроллер теперь сам отвечает 401 только для
`?all=1` без токена.

### Баг B: невалидный ObjectId давал 500

**Симптом:** `GET /api/news/not-an-object-id` → 500 (CastError в Mongoose).

**Причина:** `News.findById('не-24-символа')` бросает CastError, который ловился
как «ошибка сервера».

**Решение:** до запроса к БД проверяем формат id регуляркой
`^[0-9a-fA-F]{24}$` → 404 «Новость не найдена» в `getNewsById`, `updateNews`,
`deleteNews`. Также `isOwner` обёрнут в `Boolean(req.user && ...)`, чтобы гость
без токена не падал на `req.user.userId`.

### ESLint: `react-hooks/set-state-in-effect`

`npm run lint` (скрипт `eslint`) нашёл 4 ошибки: синхронный `setState` в теле
`useEffect` (AuthContext, editor/page, page) и `<a href="/">` вместо `<Link>`.

**Почему это важно:** синхронный setState в эффекте вызывает каскадный
пере-рендер (правило из React 19). Исправлено через ленивые инициализаторы
`useState(() => ...)` и перенос сброса loading в обработчик вкладки. `<a>`
заменён на `<Link>` (клиентская навигация Next.js).

Итог: `npm run lint` → **0 errors** (2 допустимых `no-img-element` warning —
изображения приходят из `/uploads`, `next/image` для них избыточен);
`npm run build` → зелёный.

## 8. Проверка перед сдачей

```bash
cd frontend && npm run lint && npm run build
```

Lint должен показать 0 ошибок, сборка — зелёной: TypeScript без ошибок,
все маршруты собраны.

Ручной e2e-сценарий (HANDOVER, раздел 5):

1. Регистрация нового пользователя.
2. Создание статьи (текст, картинка, цитата, код, файл).
3. Сохранение черновика → проверить вкладку «Мои» (бейдж «Черновик»).
4. Отложенная публикация → бейдж «Отложено».
5. «Опубликовать сейчас» → бейдж «Опубликовано», статья видна во «Всех».
6. Просмотр статьи → кнопки «Редактировать»/«Удалить» видны автору.
7. Редактирование → `/editor?id=...` подставил заголовок/блоки → сохранение = PUT.
8. Удаление → confirm → редирект на главную.
9. Вторая вкладка — колокольчик получает `news:created/updated/deleted`.
