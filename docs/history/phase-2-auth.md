## 2. Ключевые концепции

### 2.1. Почему пароль хранится как «хеш», а не как есть?

Если хранить пароли открыто и база утечёт — все аккаунты скомпрометированы. Поэтому пароль **никогда** не хранится: хранится только **хеш** — результат односторонней функции.

**Хеш** — это «отпечаток»: из данных получается строка фиксированной длины, по которой **нельзя** восстановить исходные данные. Одинаковые данные дают одинаковый хеш, но даже чуть изменённые — совершенно другой.

Зачем **соль (salt)**? Без соли одинаковые пароли у разных пользователей дают одинаковый хеш — злоумышленник по таблицам радужных хешей мгновенно вычислит слабые пароли. `bcrypt` добавляет случайную соль: **одинаковые пароли дают разные хеши**, а перебор замедлен — bcrypt намеренно «медленный» (при `SALT_ROUNDS = 10` хеширование занимает сотни миллисекунд). Для файла с 10 млн паролей атака перебором становится непрактичной.

**Альтернативы bcrypt:**
- **Простой MD5/SHA-256** — мгновенно, но именно поэтому не годится для паролей: перебор тривиален.
- **PBKDF2** (встроен в Node) — тоже замедляется итерациями, но менее устойчив к GPU-атакам.
- **Argon2** — современнее и «устойчивее», но требует нативного модуля.

Для учебного проекта и стандарта индустрии `bcrypt` — разумный выбор (и в ТЗ явно указан).

### 2.2. JWT — как «пропуск с подписью»

**JWT** (JSON Web Token) — строка из трёх частей, разделённых точками:

```
header.payload.signature
```

| Часть | Что содержит |
|---|---|
| **header** | тип токена и алгоритм подписи (например, `{"alg":"HS256","typ":"JWT"}`) |
| **payload** | полезные данные: `{ userId, iat, exp }` |
| **signature** | подпись: `HMACSHA256(header + "." + payload, JWT_SECRET)` |

**Как это работает:**

1. Пользователь логинится → сервер создаёт payload `{ userId: "...", iat: now, exp: now+7d }` и подписывает секретом `JWT_SECRET`.
2. Клиент получает токен и хранит его.
3. При каждом запросе клиент шлёт заголовок: `Authorization: Bearer <токен>`.
4. Сервер вызывает `jwt.verify(token, JWT_SECRET)` — пересчитывает подпись и сверяет. Если подпись совпала — значит, токен **не подделывали** (секрет есть только у сервера). Если `exp` истёк — токен невалиден.

**Почему это «stateless»?** Сервер **не хранит сессии** в памяти/БД — вся информация в самом токене. Это позволяет масштабировать сервер горизонтально (несколько инстансов — любой проверит токен) и не думать о синхронизации сессий.

**Почему payload содержит только userId?** В токен не кладут пароли и прочую чувствительность: payload, хоть и подписан, **не зашифрован** — его можно прочитать, раскодировав base64. Поэтому в нём только идентификатор, а остальное достаём из БД.

**Что хранит наш проект от тебя?**

```
secret payload: { "userId": "...", "iat": ..., "exp": ... }
```

Из токена мы получаем `userId` — ровно по ТЗ.

### 2.3. Middleware проверки токена — «охранник»

В `app.js` каждый `app.use()` добавляет «станцию» на конвейер. В `auth.routes.js` мы делаем то же для конкретного маршрута:

```js
router.get('/me', authMiddleware, authController.getMe);
```

Это значит: запрос на `/api/auth/me` сначала проходит через `authMiddleware`, и **только если токен валиден** — попадает в `getMe`. `authMiddleware`:

1. Достаёт заголовок `Authorization`.
2. Проверяет формат `Bearer <token>`.
3. Вызывает `jwt.verify(token, secret)`.
4. При успехе `req.user = payload` (там `userId`) → `next()`.
5. При ошибке — `401` и стоп.

Тот же middleware в фазе 3 навесим на все news-маршруты: «только для авторизованных».

### 2.4. Схема Mongoose: `unique`, `select: false`, `timestamps`

```js
email: { type: String, required: true, unique: true, lowercase: true, trim: true },
passwordHash: { type: String, required: true, select: false }
```

- `unique: true` — в MongoDB создаётся уникальный индекс на email: дубликат физически невозможен.
- `lowercase: true` — храним email в нижнем регистре, чтобы «User@x.com» == «user@x.com» (аудит регистра «не светит»).
- `select: false` — это «секретное» поле: обычные запросы `find()` его **не возвращают**. Чтобы получить — нужно явно `.select('+passwordHash')` (мы так делаем в `login`). Это защита от случайной утечки хеша.
- `timestamps: true` — mongoose сам добавит `createdAt` и `updatedAt`.

### 2.5. `toObject()` и удаление `passwordHash` перед ответом

```js
const userData = user.toObject();
delete userData.passwordHash;
```

`user` — это **документ Mongoose**, у него нет простых «полей». `toObject()` превращает его в обычный JS-объект, у которого уже можно `delete`. Зачем удалять? Чтобы **даже потенциальный** хеш не отправился клиенту. Плюс у документа с `select: false` поля passwordHash и так нет; но явный `delete` — страховка (у нас два слоя).

### 2.6. Универсальная ошибка при логине — «не светим email»

```js
if (!user) return res.status(401).json({ message: 'Неверный email или пароль' });
if (!isMatch) return res.status(401).json({ message: 'Неверный email или пароль' });
```

Обе ветки отвечают **одинаково**. Зачем? Если бы мы писали «Пользователь не найден» vs «Неверный пароль» — злоумышленник по ответам перебирал бы существующие email. Одинаковый ответ скрывает информацию.

### 2.7. `status` коды

| Код | Когда |
|---|---|
| 201 | Успешное создание (регистрация) |
| 400 | Невалидные данные запроса (нет email/пароля, короткий пароль) |
| 401 | Нет/невалиден токен, неверные учётные данные |
| 409 | Конфликт: email уже занят |
| 500 | Ошибка сервера |

## 3. Структура файлов (и почему так)

```
backend/src/
├── models/
│   └── User.js                  # схема пользователя + метод comparePassword
├── controllers/
│   └── auth.controller.js       # логика: register, login, getMe
├── middleware/
│   └── auth.middleware.js       # проверка JWT
├── routes/
│   └── auth.routes.js           # привязка URL → контроллер + middleware
└── app.js                       # подключение роутера: app.use('/api/auth', authRoutes)
```

Это классический паттерн **MVC** (Model-View-Controller): модель — данные; контроллер — логика; роутер — «навигация». View у нас нет: API отдаёт JSON.

**Почему так разделено?**
- Модель знает, как хранить данные (схема).
- Контроллер знает, что делать с запросом (бизнес-логика).
- Middleware знает, как пропустить/не пропустить (безопасность).
- Роутер знает, какой URL на что ведёт.

Меняй только нужный слой, не трогая остальные.

## 5. Альтернативы, которые мы рассмотрели (и почему нет)

| Решение | Альтернатива | Почему выбрали так |
|---|---|---|
| **bcrypt** | MD5/SHA-256 (мгновенно), PBKDF2, Argon2 | bcrypt — стандарт для паролей: соль + замедление перебора; указан в ТЗ |
| **JWT** | Server-side сессии (sessionId + Redis/память) | JWT — stateless: не нужно хранить сессии, легко масштабировать; указан в ТЗ |
| **payload только userId** | Класть в токен email/роль | Токен не зашифрован — минимум чувствительных данных |
| **`select: false` для passwordHash** | Отправлять хеш клиенту «он же случайный» | Лучше не отправлять вовсе — слои защиты |
| **Универсальная ошибка при логине** | Разные сообщения «email не найден» / «пароль неверен» | Не «светим», какой email существует в системе |
| **`.select('+passwordHash')` только в login** | Всегда выбирать хеш | Избегаем лишней работы и риска |
| **Хранить пароль как есть** | — | Категорически нельзя: утечка = все аккаунты |
