## 1. Что мы сделали и зачем

ТЗ (звёздочка): «*Создать раздел “уведомления” или “колокольчик” для отображения изменений в новостных статьях (real-time)*».

На сервере (фаза 5) контроллер новостей при каждом создании/изменении/удалении вызывает `getIO().emit('news:created'/'news:updated'/'news:deleted', { id, title, status })`. Теперь **клиент** подключается к этому же сокету и показывает уведомления в колокольчике.

| Событие сервера | Что видит пользователь |
|---|---|
| `news:created` | «Создана новость: <заголовок>» |
| `news:updated` | «Изменена новость: <заголовок>» |
| `news:deleted` | «Удалена новость: <заголовок>» |

## 2. Ключевые концепции

### 2.1. У клиента — один Socket.io-клиент

На бэкенде у нас `Server` (socket.io). На фронтенде — `io(baseURL)` из `socket.io-client`. Пакет один, API симметричный: сервер **эмитит** (`io.emit`), клиент **слушает** (`socket.on`).

Наш URL: `NEXT_PUBLIC_API_URL = http://localhost:5000` — тот же, что у axios. Подключение с `transports: ['websocket']` и автоматическим переподключением.

### 2.2. Почему провайдер (Context), а не подключение в каждом компоненте?

Колокольчик — не единственное место, где могут понадобиться события. Если бы каждый компонент создавал своё соединение, это было бы расточительно. Поэтому:

- **NotificationsProvider** (оборачивает приложение в `layout.tsx`) создаёт сокет **один раз** при монтировании;
- слушатели кладут события в `notifications[]` (useState);
- любой компонент через `useNotifications()` читает список и очищает его.

Это тот же паттерн «синглтон-контекст», что и `AuthContext`.

### 2.3. `typeof window !== 'undefined'` — защита от SSR

Next.js рендерит страницы и на сервере, где нет браузера, `WebSocket`, `localStorage`. Если бы мы безусловно вызывали `io()` внутри `useEffect`, это было бы ок (эффекты на сервере не выполняются), но страховка всё равно нужна — на всякий случай, и чтобы код был явно «клиентским» по намерению.

### 2.4. Колокольчик (Bell) — чисто UI

`Bell.tsx` — компонент-«витрина» данных из провайдера:

- жёлтый/красный бейдж с числом непрочитанных (`unreadCount`);
- при клике — выпадающая панель со списком последних уведомлений;
- кнопка «Очистить» (сбрасывает массив).

Анимация «встряски» при появлении нового уведомления — `@keyframes bell-shake` (из DESIGN.md).

## 5. Альтернативы, которые мы рассмотрели (и почему нет)

| Решение | Альтернатива | Почему выбрали так |
|---|---|---|
| **Провайдер-контекст (один сокет)** | Соединение в каждом компоненте | Один канал на приложение — экономно и просто |
| **Хранение уведомлений в памяти (useState)** | localStorage/БД | Уведомления сессии не обязаны переживать перезагрузку; отсутствие БД на клиенте |
| **socket.io-client** | fetch-поллинг каждые N секунд | Поллинг — это «активный опрос», а не real-time; сокет мгновенный |
| **`transports: ['websocket']`** | Лонг-поллинг по умолчанию | WebSocket экономит ресурсы, в dev достаточен |
