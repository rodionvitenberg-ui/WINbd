## 1. Что мы сделали в этой фазе и зачем

Фаза 0 — это «фундамент»: мы **ничего не собираем запускать**, но закладываем то, на что будет опираться весь проект:

1. **Правила для агентов и разработчиков** (`.clinerules.md`, `CLAUDE.md`) — чтобы любой будущий ИИ-агент (или человек) работал одинаково: не ломал архитектуру, писал по-русски, объяснял решения, не выдавал код пачками.
2. **Дизайн-систему** (`DESIGN.md`) — чтобы фронтенд не выглядел «как попало», а имел единый визуальный язык: цвета, шрифты, компоненты.
3. **Манифесты** (`ROADMAP.md`, `PROGRESS.md`, `CHANGELOG.md`) — план, журнал прогресса и историю изменений.
4. **Учебник этой фазы** (этот файл) — твою «историю разработки».
5. **Репозиторий на GitHub** — требование ТЗ: «откомментировать код в JSDoc и выложить на github».

Почему это делается *до* кода? Потому что **правила, которые появляются постфактум, не работают**. Сначала договариваемся, как работаем, — потом пишем код. Иначе через месяц проект превратится в кашу из разных стилей.

## 2. Ключевые концепции этой фазы

### 2.1. Что такое monorepo?

**Monorepo** (от англ. *monolithic repository* — «монолитный репозиторий») — это хранение нескольких проектов в одном git-репозитории.

У нас два самостоятельных «подпроекта»:

| Каталог | Что это | Технологии |
|---|---|---|
| `./backend` | Серверная часть (API) | Node.js, Express, MongoDB |
| `./frontend` | Клиентская часть (SPA) | React, Vite |

**Альтернативы:**
- **Два отдельных репозитория** (`WINbd-backend`, `WINbd-frontend`) — каждый живёт своей жизнью, свои issues, свои PR. Минус: сложнее держать синхронизацию, когда фронт и бэк меняются вместе.
- **Monorepo (наш выбор)** — один репозиторий, общая история, легче видеть картину целиком. Для учебного проекта это идеально: ты видишь весь стек в одном месте.

Для серьёзных продуктов с десятками сервисов существуют инструменты монорепозиториев (Turborepo, Nx, pnpm workspaces). Нам они пока не нужны — у нас два каталога, и npm-скрипты в каждом запускаются отдельно.

### 2.2. `.clinerules.md` — почему это отдельный файл, а не правка глобального?

У тебя есть **глобальные** правила в `/home/rodion/Documents/Cline/Rules/` — они применяются ко *всем* твоим проектам. Но этот проект особенный:

- стек другой (Node.js + MongoDB вместо Django + Next.js);
- режим обучения (нужно объяснять каждый шаг);
- все комментарии на русском;
- история разработки по фазам.

Если бы мы вписали это в глобальные правила — они бы мешали в остальных проектах. Поэтому создаём **локальный** `.clinerules.md` в корне `WINbd`: агент, работающий здесь, сначала читает его. **Правило в нём:** «Глобальный файл не трогаем».

Иерархия правил: глобальные → локальные проекта → задача. Локальные уточняют глобальные, но не отменяют их (например, «неинтерактивный терминал» — это глобальное требование, оно перешло в наш локальный файл).

### 2.3. Зачем «история разработки» в отдельном файле на фазу?

Ты просил: «создавать ИСТОРИЮ разработки. Отдельный файл для отдельной фазы, а фазу ты описываешь языком человеческим, как учебник».

Почему отдельный файл, а не один общий? Учебник фазы — это **десятки строк объяснений**: концепции, примеры, команды, вопросы для самопроверки. Если всё свалить в один файл — он станет нечитаемым уже к фазе 3. Каталог `docs/history/phase-XX-*.md` даёт структуру: хочешь вспомнить, как устроен JWT? — открываешь `phase-2-auth.md`.

Зачем форма «учебника»? Потому что **запись, сделанная «по горячим следам», сохраняет контекст**: через месяц ты не вспомнишь, почему отложенная публикация — это фильтр, а не таймер. А в учебнике это зафиксировано словами и примерами.

### 3.2. `CLAUDE.md` — сводка «на бегу»

Это шпаргалка: стек, команды, домен. Агент, который уже знает правила, может работать только по `CLAUDE.md`, не перечитывая `.clinerules.md` целиком. Плюс это стандарт индустрии: `CLAUDE.md` — первый файл, который читает ИИ-агент при старте работы в репозитории.

### 3.3. `DESIGN.md` — дизайн-система

Важно понимать: **дизайн-система — это не CSS-файл**, это *документ о договорённостях*. Он отвечает на вопросы:

- Какие цвета? (тёмная тема: фон `#0f1115`, акцент `#4f8cff` и т.д.)
- Какая типографика? (системные шрифты, размеры)
- Как выглядят кнопки, карточки, бейджи?
- Какие анимации?

Почему именно тёмная тема? Редактор статей — инструмент, за которым сидят долго (как редактор кода). Светлая тема утомляет глаза при длительной работе. Это осознанное решение, а не «модно». (Кстати, Medium — светлый, Notion — поддерживает обе темы. Мы выбрали тёмный как базу — в `DESIGN.md` это зафиксировано.)

## 4. git и GitHub — что это и зачем

### 4.1. git — система контроля версий

**git** — программа, которая следит за изменениями файлов. Представь «машину времени» для проекта:

- **`commit`** — «снимок» состояния проекта в момент времени. Как точка сохранения в игре.
- **`branch`** — отдельная линия разработки. Можно делать фичи отдельно, не ломая основную.
- **`merge`** — слияние веток.
- **`push`** — отправка коммитов в удалённый репозиторий (GitHub).
- **`pull`** — забрать изменения к себе.

Зачем это нам?
1. **Требование ТЗ** — «выложить на github».
2. **Возможность вернуться** к любой точке разработки.
3. **История проекта** — каждый коммит = объяснение «что и зачем поменялось».

**Альтернативы git:** Mercurial, SVN, Fossil. Но git — фактический стандарт индустрии, его понимание обязательно.

### 4.2. GitHub — облачный сервис для git-репозиториев

**GitHub** — это «git в интернете» + веб-интерфейс + куча инструментов (issues, PR, Actions). Позволяет:

- хранить репозиторий в облаке (бэкап и шаринг);
- показывать проект работодателю/заказчику;
- работать из нескольких мест.

**Альтернативы:** GitLab, Bitbucket, Gitea. GitHub — самый популярный, для портфолио это плюс.

### 4.3. Основные команды git, которые мы будем использовать

| Команда | Что делает |
|---|---|
| `git init` | Создать репозиторий в текущей папке (появляется скрытая папка `.git/`) |
| `git status` | Показать, что изменилось |
| `git add <файл>` | Добавить файл в «индекс» (в корзину подготовки) |
| `git add .` | Добавить все изменения |
| `git commit -m "сообщение"` | Создать снимок с сообщением |
| `git log --oneline` | Показать историю коммитов |
| `git branch -M main` | Переименовать текущую ветку в `main` |
| `git remote add origin <url>` | Привязать удалённый репозиторий |
| `git push -u origin main` | Отправить коммиты на GitHub (в первый раз) |
| `git push` | Отправить в следующий раз |

Понимание потока: `git add` → `git commit` → `git push`. Это три шага «сохранить локально → сохранить в истории → отправить в облако».

### 4.4. `.gitignore` — какие файлы НЕ попадают в git

В git нельзя пушить секреты и мусор:

- `.env` — файл с паролями и ключами! В репозиторий кладём только **шаблон** `.env.example` (с пустыми заглушками).
- `node_modules/` — тысячи зависимостей, восстанавливаются командой `npm install`.
- Папки с временными файлами.

Поэтому создадим `.gitignore`:

```
node_modules/
.env
uploads/**
!uploads/.gitkeep
.DS_Store
*.log
```

Почему `uploads/**` + `!uploads/.gitkeep`? Мы хотим, чтобы папка `uploads` существовала в репозитории, но была пустой. git не хранит пустые папки, поэтому кладём внутрь пустой файл `.gitkeep` (соглашение названия).

### 4.5. Почему имя ветки `main`, а не `master`?

Исторически основная ветка называлась `master`. В 2020 году GitHub изменил дефолт на `main` — нейтральное имя. Мы сразу создаём `main`.

## 5. Что такое npm и package.json

### 5.1. npm — менеджер пакетов Node.js

**npm** (Node Package Manager) — программа, которая управляет библиотеками JS:

- `npm init` — создать `package.json` (манифест проекта);
- `npm install <pkg>` — установить пакет и записать его в `package.json`;
- `npm run <script>` — выполнить скрипт из `package.json`.

### 5.2. `package.json` — документ «что за проект»

```json
{
  "name": "winbd-backend",
  "version": "1.0.0",
  "description": "REST API редактора новостных статей",
  "main": "src/server.js",
  "scripts": {
    "dev": "nodemon src/server.js",
    "start": "node src/server.js"
  }
}
```

- `scripts.dev` — запуск в разработке: `nodemon` перезапускает сервер при изменении файлов. Не нужно вручную перезапускать.
- `scripts.start` — обычный запуск `node`, для продакшн-сервера.

> Здесь фиксируем ВСЕ команды, которые реально выполнялись. Это требование — чтобы история была проверяемой и воспроизводимой.

### 6.1. Инициализация git и первый коммит

```bash
# 1. Создаём репозиторий в текущей папке WINbd
git init

# 2. Смотрим статус: какие файлы новые/изменённые
git status

# 3. Добавляем все файлы в индекс
git add .

# 4. Делаем первый коммит
git commit -m "Фаза 0: правила, манифесты, дизайн-система, README"
```

### 6.2. Создание репозитория на GitHub

Репозиторий создаёт агент через GitHub MCP (у нас есть сервер `github`). После создания — привязываем и пушим:

```bash
# Переименовываем ветку в main (если называется иначе)
git branch -M main

# Привязываем удалённый репозиторий
git remote add origin https://github.com/<твой-аккаунт>/WINbd.git

# Отправляем; -u запоминает связь ветки с origin
git push -u origin main
```

> Дальше просто: `git add . && git commit -m "..." && git push`.

| Решение | Альтернатива | Почему выбрали так |
|---|---|---|

| **Тёмная тема дизайна** | Светлая «как Medium» | Редактор — инструмент длительной работы |

| **`.env.example` в git, `.env` — нет** | Класть `.env` в репозиторий | Секреты нельзя пушить (безопасность) |
